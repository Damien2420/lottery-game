# 彈珠台抽獎 Next.js 改版設計

日期：2026-11-06

## 1. 目的與動機

現有專案是一個 Vite + TypeScript 的單頁彈珠台抽獎工具：貼上名單、按下開始，彈珠落下，前 N 名抵達終點者得獎。它沒有首頁、無法保存資料，也不容易被搜尋引擎找到。

這次改版要達成三件事：

1. **能被搜尋到**：加入一個以「抽獎彈珠台」為主要關鍵字的首頁，靠 SEO 帶進使用者。
2. **能保存與重用**：使用者第二次來時，可以直接選用上次的名單，並翻看過去的抽獎紀錄、重播當時的過程。
3. **學習 Next.js**：作者希望藉這個專案學習 Next.js（App Router），因此技術選型採用 Next.js，即使目前沒有後端需求。

## 2. 目標、非目標、反目標

### 目標

- 首頁在建置時預先產生為靜態 HTML，具備完整 SEO 設定。
- 使用者可以建立、編輯、刪除、複製多份參加者名單。
- 提供 3 種預設彈珠台台面供每次抽獎選擇。
- 每場抽獎自動存成歷史紀錄，可查看得獎排名並重播。
- 所有資料存在瀏覽器 localStorage，可匯出／匯入 JSON 備份。
- 保留現有體驗：物理模擬、鏡頭跟隨、領先者白框、碰撞音效、勝利旋律、彩帶。

### 非目標（這次不做）

- 登入、帳號、任何後端 API 或資料庫。
- 跨裝置、跨瀏覽器的自動同步（以匯出／匯入 JSON 代替）。
- 使用者自行設計台面的編輯器。
- 繁體中文以外的語系。
- 自有網域（先用 Vercel 提供的 `*.vercel.app` 網址）。

### 反目標（即使功能可用，發生就算失敗）

- **重播改寫了原始結果**：歷史紀錄中的得獎排名一經寫入就不可被重播結果覆蓋。
- **使用者資料離開瀏覽器**：名單與紀錄不得傳送到任何伺服器。首頁會對使用者宣稱「資料只存在你的瀏覽器」，這句話必須為真。
- **抽獎結果可被預測或指定**：種子必須在按下開始時才以密碼學亂數產生，不可由使用者輸入或事先得知。（中途重新整理重抽的情況見第 6 節，屬於已接受的風險。）

## 3. 限制

- **框架**：Next.js（App Router）+ TypeScript，直接在現有 `lottery-game` repo 中改寫，移除 Vite。
- **部署**：Vercel，透過 GitHub 整合自動部署。網站網址以環境變數 `NEXT_PUBLIC_SITE_URL` 提供，未來換自有網域只需改設定。
- **沒有伺服器端資料**：所有使用者資料只在瀏覽器端讀寫。凡是讀取 localStorage 的元件都必須是客戶端元件，且不可在伺服器端渲染時讀取，以避免 hydration 不一致。
- **人數上限**：每場最多 200 人（沿用現有 `MAX_PLAYERS`）。
- **物理引擎**：沿用 Matter.js，版本需鎖定為精確版本（不使用 `^`），因為版本變動會影響重播結果。

## 4. 頁面與使用流程

### 頁面

| 路徑 | 渲染方式 | 搜尋引擎收錄 | 內容 |
|---|---|---|---|
| `/` | 靜態產生 | 收錄 | 首頁（見第 7 節） |
| `/play` | 客戶端 | 不收錄 | 抽獎頁：選名單、選台面、設定名額，開始抽獎 |
| `/lists` | 客戶端 | 不收錄 | 名單管理：列表、新增、編輯、刪除、複製 |
| `/history` | 客戶端 | 不收錄 | 歷史紀錄列表與單場詳情、重播 |
| `/settings` 或併入其他頁 | 客戶端 | 不收錄 | 匯出／匯入 JSON 備份 |

由於資料的 ID 只存在瀏覽器中，伺服器無法預先產生 `/lists/[id]` 這類動態路由頁面。指定單筆資料時請用查詢參數，例如 `/history?id=xxx`。

### 第一次使用

1. 從首頁點「開始抽獎」進入 `/play`。
2. 沒有任何名單時，直接在抽獎頁貼上名單（一行一位），並可命名後存成一份名單。
3. 選擇台面、抽出名額、是否自動移除得獎者、是否開啟音效。
4. 開始抽獎。結束後自動寫入一筆歷史紀錄。

### 之後再來

1. 進入 `/play`，從下拉選單選擇已存的名單（可直接修改），或建立新名單。
2. 選擇台面（預設帶入上次使用的台面）。
3. 開始抽獎，或到 `/history` 翻看與重播過去的紀錄。

## 5. 資料模型

所有資料存在單一 localStorage key 中（例如 `pinball-lottery`），內容為帶版本號的 JSON，以便日後調整結構時能遷移舊資料。

```ts
interface StoredData {
  /** 資料結構版本，日後遷移用 */
  schemaVersion: 1;
  lists: ParticipantList[];
  draws: DrawRecord[];
  /** 偏好設定：上次使用的台面、音效開關等 */
  preferences: { lastBoardId?: string; sound: boolean; removeWinners: boolean };
}

/** 一份參加者名單 */
interface ParticipantList {
  id: string;
  title: string;
  /** 一個元素一位參加者，允許同名 */
  names: string[];
  createdAt: string; // ISO 8601
  updatedAt: string;
}

/** 一場抽獎紀錄，寫入後不可修改，只能刪除 */
interface DrawRecord {
  id: string;
  createdAt: string;
  /** 來源名單 ID；名單之後可能已被刪除，僅供參考 */
  listId: string | null;
  /** 抽獎當下的名單標題與參加者快照，重播只依賴此快照 */
  listTitle: string;
  names: string[];
  boardId: string;
  boardVersion: number;
  /** 引擎版本：物理參數、模擬邏輯、亂數演算法或 Matter.js 版本任一變動即升版 */
  engineVersion: number;
  winnerCount: number;
  /** 32 位元無號整數，以 crypto.getRandomValues 產生 */
  seed: number;
  /** 得獎者依抵達順序排列，對應 names 的索引（支援同名） */
  winners: number[];
}
```

### 規則

- **得獎排名只記錄前 N 名得獎者**，不記錄所有人的完整名次。
- **在抽獎頁修改名單**：選了已存的名單後，可以直接在抽獎頁修改內容，按下開始時覆蓋原名單並更新 `updatedAt`。若使用者想保留原版，請到名單管理頁使用「複製」。直接貼上、尚未存檔的名單，就只是一個可自由編輯的文字框。
- **修改名單不影響歷史紀錄**：每筆紀錄都存有當下的名單快照，名單之後被修改或刪除，都不影響舊紀錄的顯示與重播。
- **「得獎者自動從名單移除」**勾選時，抽獎結束後修改本場使用的名單：若是已存名單，修改存檔；若是未存檔的文字框，就刪掉文字框中的對應行。每位得獎者只移除一筆，以支援同名的不同參加者。
- **歷史紀錄**寫入後不可編輯，可個別刪除。
- **localStorage 不可用或容量已滿**（例如無痕模式、空間不足）時，抽獎仍要能進行，但需明確提示使用者「本次結果無法保存」，不可默默失敗。

## 6. 抽獎引擎與重播

### 可重現性要求

重播採用「種子重新模擬」，不儲存彈珠軌跡。為了讓同一個種子在同一瀏覽器上一定跑出相同結果，現有引擎必須修正以下問題：

1. **所有影響物理的亂數都改用可帶種子的亂數產生器**，包含洗牌、起跑位置偏移、卡住時的推動。音效使用的亂數必須和物理亂數分開，確保音效開關不影響結果。
2. **每場抽獎建立全新的 Engine 與台面物件**，不沿用上一場的狀態（物件 ID、碰撞配對快取）。
3. **旋轉擋板每場從初始角度開始**。目前擋板在非抽獎期間也持續旋轉，導致每場起始角度不同，必須改掉。
4. **模擬進度只以物理步數推進**，不依賴實際經過的時間。顯示速度可以變（例如分頁切到背景），但第 k 步的物理狀態必須相同。
5. **同一步內多顆彈珠同時越過終點線時的名次規則要明確且具決定性**：依 y 座標由大到小排序，相同時依彈珠在洗牌後的索引排序。
6. **鎖定 Matter.js 精確版本**，並維護兩種版本號：台面配置變動時升 `boardVersion`；物理參數（限速、卡住判定、保險桿彈力、彈珠材質）、模擬步進邏輯、亂數演算法或 Matter.js 版本變動時升 `engineVersion`。

### 抽獎流程

1. 按下開始時，以 `crypto.getRandomValues` 產生種子。
2. 以「名單快照 + 台面 + 種子」建立模擬，前 N 名抵達即結束。結束後寫入 `DrawRecord`。
3. **中斷不留紀錄**：抽獎進行中若頁面重新整理、關閉或離開，這場視為中斷作廢，不寫入任何資料，也不修改名單。理由是未跑完的抽獎沒有被所有人看到結果，不應成立。抽獎進行中離開頁面時，應以瀏覽器的離開確認提示使用者「抽獎尚未結束，離開將作廢本場」。

已知且接受的風險：主持人可以在結果不如意時重新整理頁面重抽，且不留痕跡。這是作者明確選擇的取捨。

### 重播流程

1. 以紀錄中的名單快照、`boardId`、`boardVersion`、`seed`、`winnerCount` 重新模擬並播放動畫。
2. 播放結束後，比對模擬出來的得獎者與紀錄中的 `winners`：
   - 一致：正常顯示。
   - 不一致：**以紀錄為準**，並在畫面明確提示「此重播與原始結果不同（可能因瀏覽器或版本差異）」。
3. 若紀錄的 `boardVersion` 或 `engineVersion` 和目前程式的版本不同，重播前直接提示「台面或引擎已更新，無法精確重播」，仍可顯示得獎排名。

### 已知限制

`Math.sin`、`Math.cos` 等函式在不同瀏覽器的計算結果，規格並未保證每一位都相同，因此跨瀏覽器重播可能出現差異。這是可以接受的，由上面的比對與提示機制處理。

## 7. 台面

- 上線時提供 **3 種**預設台面，各自有不同的軌道走向與障礙物配置（釘陣、斜坡、旋轉擋板、保險桿、漏斗的組合與位置）。現有台面可作為其中一種。
- 每種台面的定義包含：`id`、顯示名稱、`version`、建立函式。
- 每種台面都必須能容納 200 顆彈珠的起跑區。
- **驗收**：用無頭模擬（`scripts/simulate.ts`，需改為可指定台面）每種台面以 200 顆彈珠跑多場，全部抵達終點，且沒有長時間塞住的區段。各台面跑完一場所需時間不能相差太多，不要讓任一台面明顯拖慢。
- 無頭模擬必須和正式遊戲共用同一份物理參數與模擬步進程式碼，不可像現在一樣各自寫死一份。

## 8. 首頁與 SEO

### 首頁內容

- 主標題與一句話說明，例如「免費線上抽獎彈珠台，貼上名單就能開抽」，並放置「開始抽獎」按鈕。
- 自動播放的彈珠台示範動畫，使用範例名單，預設靜音。這段動畫要在首屏內容顯示後才載入，不可拖慢首頁載入。
- 特色介紹：免註冊、最多 200 人、可重播、資料只存在自己的瀏覽器。
- 三步驟使用說明。
- 常見問題，例如：公平嗎、資料會被上傳嗎、最多可以抽幾個人、換電腦資料還在嗎。

### 目標關鍵字

主要關鍵字是「抽獎彈珠台」，另外搭配「線上抽獎」、「彈珠抽獎」、「抽獎工具」、「尾牙抽獎」。目標使用者是在台灣辦活動的人，例如公司尾牙、社團、直播、班級。

### 技術設定

- 使用 Next.js Metadata API 設定各頁的 title、description、canonical。
- Open Graph 與 Twitter 分享預覽圖。
- `sitemap.xml` 只列首頁，`robots.txt` 指向 sitemap。
- `/play`、`/lists`、`/history` 等個人頁面設為 `noindex`。
- 常見問題加上 `FAQPage` 結構化資料（JSON-LD）。
- `<html lang="zh-Hant">`。

## 9. 從現有程式碼遷移

- `game.ts`、`board.ts`、`audio.ts` 盡量保留原有邏輯，搬到 Next.js 專案中，例如放在 `src/lib/pinball/`，並依第 6 節修正可重現性問題。
- `Game` 必須新增銷毀方法，負責停止 `requestAnimationFrame`、解除 `ResizeObserver`、清除物理世界。React 元件卸載時呼叫。React 開發模式會刻意將元件掛載兩次，必須確認不會出現兩個畫面迴圈。
- 彈珠台元件只在瀏覽器端載入，不參與伺服器端渲染。
- `main.ts` 的 DOM 操作改寫為 React 元件。
- 移除 Vite 相關的檔案與相依套件。
- `scripts/simulate.ts` 要納入型別檢查，並把所需工具（例如 `tsx`）加入 devDependencies。
- README 更新為新的啟動、建置與部署方式。

## 10. 留給實作者決定

以下事項由實作者自行判斷，不需回頭確認：

- 樣式方案（CSS Modules、Tailwind 等）與整體視覺設計。整體需在桌機與手機上都能操作，抽獎主要情境是桌機投影。
- 可帶種子的亂數產生器選用哪個演算法。
- 3 種台面的具體配置。
- 名單、紀錄頁的版面與互動細節。
- 匯入 JSON 時的行為。建議做法：先驗證格式與版本，經使用者確認後整份取代現有資料。
- 重播是否提供加速、略過動畫等控制。
- 分享預覽圖的設計。
- 測試範圍。至少要涵蓋：資料讀寫與遷移、同一種子跑兩次得到相同得獎者、名單移除得獎者的同名處理。
